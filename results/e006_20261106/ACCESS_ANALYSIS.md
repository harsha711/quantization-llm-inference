# E006 access and synchronization analysis

Source: untouched vLLM v0.33.0 `4ba787ec9959e566d3b587a796dff07673324da5`, archived in E005. Line numbers below refer to that archive. This is a lifetime analysis, independent of E005's spatial bounds proof. Initial analysis recorded before testing the single barrier patch.

## 1. Conflicting phases

The failing specialization is dense FP16/uint4b8/FP16/FP16, threads=256, thread_m_blocks=1, thread_n_blocks=8, thread_k_blocks=8, m8=true, stages=4, group_blocks=8, is_zp_float=false. Source B and reduction pointers both equal `sh_new` (lines 698–716). FP16 makes `sh_new=sh`. All addresses in this paragraph are relative to that dynamic shared origin. Four B stages occupy [0,32768), 8192 bytes each. Scales occupy [32768,33792) and A [33792,41984). The actual reduction writes span up to byte 15360, within the B overlay. Bounds alone do not order these uses.

With b_sh_stride=64 int4, b_sh_stage=512 int4, b_sh_wr_iters=2 and b_thread_vecs=1, B read address in int4 units is `512*pipe + 64*(k%2) + t + 64*floor(t/64)`, where t is threadIdx.x and k is the argument to fetch_to_registers. All eight warps participate. `fetch_to_registers` (832–845) emits an ordinary 16-byte shared load for B and warp-synchronous `ldmatrix.x2` loads for A. ldmatrix's warp collective does not join different warps.

Reduction has red_off=2, red_idx=floor(t/64), red_sh_stride=512 and delta=64. Its first writers are threads128–255 (warps4–7). For j={0,2,4,6}, their int4 destination is `64*j + 512*(floor(t/64)-2) + t%64`. The next i=1 round uses threads64–127, after an internal block barrier. First-round writes occur BEFORE the reduction's first barrier at 1240. That barrier orders reduction rounds. It cannot order the preceding B reads before the first overlay writes.

The first full-block diagnostic records a WAR pair at shared 0x2600, block 11: reader thread 32 (warp 1), PC 0x2bc0, source 843, versus writer thread 224 (warp 7), PC 0x4a00, source 1237. Source addresses for both equal8704 bytes. The compiled SASS establishes a dynamic shared base of0x400, so8704+1024=9728=0x2600. This is a cross-warp conflict. SASS reader `LDS.128 R36,[R92+0x2000]` and writer `STS.128 [R82+-0x4000],R20` match that pair. The other saved E005 reader PC 0x48e0 is `LDS.128 R36,[R92]`, another unrolled pipeline position. Writes0x4a10/20/30 are the other j offsets. Exact wheel instruction/source equivalence remains unestablished because the wheel lacks line information.

For terminal next-stage reads the subfragment index is zero. The stage 0 read ranges are [0,1024),[2048,3072),[4096,5120),[6144,7168). Stage 1 adds8192 to each range. The first reduction writes exactly those ranges at both bases, [0,7168) and [8192,15360) with the listed gaps. Stage 0 overlap maps reader t to writer128+(t%64) with j=2*floor(t/64). Stage 1 maps to writer192+(t%64) with the same j. Same-thread pairs do not create a cross-thread hazard. The other mappings include different warps. Stages2/3 start at 16384/24576 and do not overlap these first writes. These source-derived ranges explain both reported reader PCs. The 100 byte-level entries actually displayed in the square detailed report cover only 0x2600–0x2663, block 11, readers32–38 and writers224–230. They are a print-limited observation, not exhaustive reported thread coverage. The independent E005 grouped report supplies the second reader PC.

## 2. Terminal prefetch dataflow

The main loop (1572–1603) always fetches k+1 before computing k. For this specialization k=0 fetches register buffer1 for the current shared stage, increments pipe and executes wait_for_stage (async wait plus block barrier), then matmul0 consumes buffer0. k=1 fetches buffer0 from the NEXT stage, then matmul1 consumes buffer1. That next-stage fetch is useful only if another K tile follows. When slice_iters becomes zero, reduction consumes frag_c only. A subsequent stripe's start_pipes unconditionally replaces buffer0 before use, or the CTA terminates. Consequently the final next-stage B fragment has no source-level path to a useful matmul in this specialization. An ordinary emitted shared read still exists. This explains why the reported lifetime gap can coexist with passing output checks. It does not prove that every report on every Marlin configuration is harmless, that a data race is valid CUDA, or that the official wheel's exact dataflow is identical.

At square M8 grid36, k_tiles=32 and iters=29. Block 11 starts at K tile31 in column9 and its first slice has one tile. Its final lookahead reads stage 1, giving the observed PC 0x2bc0. At a slice length divisible by4 the next-stage read wraps to stage 0, corresponding to0x48e0. Useful B subfragments before terminal lookahead pass a block barrier in wait_for_stage before reduction entry. The unused terminal fragment does not. The same speculative pattern can read an unfilled next stage on a one-tile stripe. No attempt is made here to remove prefetches or change the pipeline.

Compiled control flow supports this source dataflow: the next-stage load at 0x2bc0 writes R36–R39, the remaining MMA at 0x2c30 consumes R44 rather than those new registers, and the terminal branch at 0x2c60 jumps to0x4970/reduction. The wraparound load at 0x48e0 similarly precedes the terminal MMA using R44 and stripe-exit test. This is not a full machine-code proof for all specializations. The analyzer checks double-buffer tags for slice lengths1–86 as a finite consistency check on the source argument.

## 3. Pending copies and proposed ordering

fetch_to_shared commits a cp.async group even when its predicate is false (810–814). wait_for_stage waits for stages−2 groups and executes a block barrier. At stripe end, cp_async_wait<0> (1660) drains all committed groups issued by the executing thread. It does not order ordinary shared reads against other threads. No block-wide join follows before reduction first writes the overlay. A fast warp may begin reuse while another warp is still reading B or draining its own copies. E006 does not claim the original report identified a pending-copy write. The measured pair is ordinary LDS versus STS.

The one proposed change inserts `__syncthreads()` immediately after that existing cp_async_wait<0>. Every thread must finish its ordinary shared reads and its own copy groups before any thread proceeds to overlay reduction. No new B copy is issued between that join and reduction for the fixed G128 path. Per-column-scale code is compile-time disabled. Thus this establishes the missing read-before-overwrite relationship and prevents prior B copies from surviving into reduction. The existing internal reduction barriers remain unchanged. Barrier-only without draining async copies, a warp-only sync, separate reduction allocation, removing terminal prefetches, and tool suppression are not selected. They either do not supply the required cross-warp dependency or change more than this bounded investigation needs.

## 4. Uniformity and paths

All predicates controlling entry to the added barrier are CTA-uniform. slice_iters, slice_row/col, part1_mn_iters, in_part2, slice_count and slice_idx derive from scalar dimensions, gridDim and blockIdx and are updated identically in every thread. Per-thread A-tail, packing, scale and reduction predicates do not modify them. The loop's break and stripe-final if depend only on slice_iters. init_part2_slice's early return is from a lambda on a uniform zero-work condition. Empty CTAs skip both the main loop and the barrier. start_pipes is called uniformly for a new nonempty stripe. Architecture guards are compile-time uniform. Helper returns in matmul/global reduction do not return from individual kernel threads. No thread exits the kernel before a peer reaches this barrier. The same argument covers M1/5/8 row tails and M16/64 fallback specializations in the bounded FP16/G128 build. Existing block-wide barriers in these same control regions are consistent with this argument, but are not its proof.

## 5. Documented semantics and targeted upstream search

[PTX cp.async.wait_group](https://docs.nvidia.com/cuda/parallel-thread-execution/#data-movement-and-conversion-instructions-cp-async-wait-group) specifies executing-thread async-group completion and no ordering for other memory operations. [PTX CTA barriers](https://docs.nvidia.com/cuda/parallel-thread-execution/#parallel-synchronization-and-communication-instructions-bar) supply a CTA-wide join and ordering of ordinary prior accesses before later ones. [Compute Sanitizer racecheck](https://docs.nvidia.com/compute-sanitizer/ComputeSanitizer/index.html#racecheck-tool) distinguishes byte-accurate hazard reports from grouped analysis reports and supports cp.async group checking. Its [release notes](https://docs.nvidia.com/compute-sanitizer/ReleaseNotes/index.html) describe various mbarrier, warp synchronization and bulk-copy fixes. None establishes a limitation applicable to this plain cross-warp LDS/STS pair with no barrier between them. Installed tool version is recorded separately. No tool limitation is inferred from general release-note language.

[vLLM issue 11205](https://github.com/vllm-project/vllm/issues/11205) concerned older v0.6.4 development code on A10G and was closed by [PR 11493](https://github.com/vllm-project/vllm/pull/11493/files), merge commit `5dba2575065f5e27d468f2776e3d460a21d916e6` (2025-01-02). That fix separated reduction storage and changed grouped-scale accesses. It is historical context, not a patch to import blindly. Later [commit 1d0c9d6b2d74e6884c6c63f4856ac0a2cddd0508](https://github.com/vllm-project/vllm/commit/1d0c9d6b2d74e6884c6c63f4856ac0a2cddd0508), PR 16850 (2025-05-05), introduced the templated implementation with sh_b and sh_red sharing sh, and the existing drain/reduce transition. Current blame shows the later W4A8 commit 1656ad3704 changed the base to sh_new, preserving the alias. The pinned release still has that transition. Local git patches/blame preserve this targeted check. No claim that all upstream branches/issues were searched.

[Original Marlin issue 42](https://github.com/IST-DASLab/marlin/issues/42) concerns per-column async scales on A100. That branch is disabled here, and no resolution is established there. [Issue 45](https://github.com/IST-DASLab/marlin/issues/45) reports nondeterministic output at group128 on sm87 in original Marlin1f25790. Hardware, source, dimensions and reported mechanism differ. It is not evidence of incorrect output in our reproducer. The search found no exact applicable sanitizer exemption or upstream one-barrier correction for the pinned specialization. No upgrade or external report was made.
