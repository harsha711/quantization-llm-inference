**My performance explanation is a hypothesis: operand preparation and insufficient reuse are limiting useful Tensor Core throughput.**

At **M128**, eight independent 16-row tiles reload and unpack each weight eight times. The packed-code load requests therefore total **64 MiB**, before scales, despite an 8 MiB code representation. Cache can absorb repeated requests, but it cannot remove their instructions or dequantization. Activations are also reread across N tiles. There is no explicit pipeline across K chunks; compiler scheduling may overlap some work, but the source provides no staged producer/consumer pipeline.

At **M1**, the kernel still executes a 16-row MMA tile: **15/16 of its row arithmetic is padding**, and it writes the full shared partial array. There are only 128 CTAs for 36 SMs. Unpacking dependencies, reduction/barrier work and finite scheduling overhead accompany the weight stream.

Recomputing the stated model gives **8,667,136 logical bytes / 448 GB/s = 19.346 µs**, against **32.416–33.120 µs** observed. That establishes the reported **0.584–0.597 logical-bandwidth ratio**; it does not measure DRAM utilization.

**I would predeclare one fixed 32×32 M tile first**, retaining the current packing, eight-way K split and unpack method. At M128 it halves repeated weight loading/unpacking while preserving substantial parallelism: 512 CTAs for the square case. My forecast is **10–20% lower M128 latency**, enough potentially to close much of the current cuBLAS gap. This is an estimate, not evidence. Register/shared-memory growth could erase it; I expect no M1 benefit.
