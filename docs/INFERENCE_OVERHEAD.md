# E014: full-model execution overhead on RTX 5060 Ti

**The investigation stops at its predeclared numerical gate. No inference speedup is accepted.** Static KV caching passes the full-model validation at both contexts. Compiled static-cache decoding passes at 128 tokens, but fails the elementwise logit check at 2048 tokens. The experiment releases neither primary nor held-out timing. This is a numerical-validation outcome, not a measured performance rejection or evidence that execution overhead cannot be reduced.

The authorized scope is one dense FP16 model, one GPU, one cache/compile comparison and fixed single-request work. The [design and acceptance criteria](EXPERIMENTS.md#e014--single-request-full-model-execution-overhead) are committed before candidate execution. E013's rejected tile stays rejected, and corrected Marlin A, old measurements, manifests and environments remain unchanged. This full-model FP16 path does not use the local W4A16 Marlin kernel. Upstream Transformers supplies the model/cache implementation, while PyTorch supplies SDPA, Inductor fusion/code generation and CUDA graph replay.

## Workload and validation

The model and tokenizer are openly accessible `Qwen/Qwen2.5-1.5B`, pinned to `8faed761d45a263340a0528343f099c05c9a4323`. The published BF16 checkpoint is loaded into the same FP16 parameters for every variant. All 1,543,714,304 parameters, their names/dtypes and FP16 value hashes are checked. Parameter storage is 3,087,428,608 bytes, or 2.8754 GiB. This is a representation choice shared by all variants, not a quantization change between them. The original model file SHA256 is `a961db72e75d52b18e6b0c9d379e51a26973b233385e0e127fdda7d648aec796`. [Model card](https://huggingface.co/Qwen/Qwen2.5-1.5B).

Use batch size 1, 128/2048 prompt tokens and 64 greedy output tokens. Primary and held-out passages are fixed in [prompts.json](../scripts/e014/prompts.json). Each passage is repeated and its token IDs truncated to the declared context length. These are controlled text workloads rather than a representative prompt distribution. The first output token comes from prefill, followed by 63 cached one-token forwards. Generation deliberately continues through EOS for equal work, with EOS positions saved. No reference request emits EOS within its 64 output tokens. Model quality, natural-EOS stopping, network service and multiuser scheduling are outside the result.

The isolated Python 3.11 environment uses PyTorch 2.14.0+cu130, Transformers 4.57.1, tokenizers 0.22.1 and safetensors 0.6.2. The [resolved lock](../scripts/e014/requirements.lock), [model/tokenizer hashes](../results/e014_20261108/model.json), preserved runtime sources and exact commands make the inputs explicit. All model variants use the same fused SDPA memory-efficient backend, verified by actual `fmha_cutlassF_f16` kernels. Math, Flash and cuDNN SDPA fallback are disabled. Explicit additive causal masks, padded for efficient-attention strides, are common to the variants. This is a reasonable supported cached baseline, but is not claimed to be the fastest attention implementation available. The explicit masks disable Transformers' mask-free GQA fast path consistently. Changing that backend or mask path would require a separate comparison.

Variant A is dynamic KV with eager decode. Variant B is static KV with eager decode. Variant C uses the same static path with `torch.compile(mode="reduce-overhead",fullgraph=True,dynamic=False)` around the forward and greedy argmax. Prefill, mask preparation and the host loop remain eager. Static capacity is context+64 and static storage is reused/reset between requests. A creates a fresh dynamic cache. An explicit common loop avoids Transformers `generate` automatically compiling a static-cache path, which would confound A/B. [Transformers 4.57.1 cache documentation](https://huggingface.co/docs/transformers/v4.57.1/en/kv_cache).

The full-model validation is separate from the unchanged GEMM contract. A supplies all-vocabulary FP16 logits at all 64 output positions, 9,723,904 values per prompt. B/C must reproduce all 64 greedy token IDs exactly and satisfy both `abs(candidate-reference) <= 0.03 + 0.01*abs(reference)` and logit relative L2 <= 0.003. All values must be finite. Primary A also agrees with uncached full-prefix forwards at output positions 0/63 under these checks. References, outputs, top-two margins and validation statistics are preserved. This checks equivalence to same-precision A, not FP64 accuracy or model quality. No tolerance changes after observation are allowed.

## What the diagnostic establishes

The c4 device is RTX 5060 Ti 16 GB/sm120, 36 SMs, GPU UUID `GPU-f2e08184-f913-0d97-104d-e01716a3c597`, driver 610.57.04. CPU is AMD EPYC 9115. One prun rank uses 16 host threads with recorded affinity/OpenMP settings. CUDA compiler 13.4.92, runtime 13.0.96 and Open MPI 4.1.6 are recorded. Current ARC documentation and live allocation state are checked before execution. All installation, model loading, inference and compiler work occurs on allocated compute, with no user-created allocation cancelled. Clocks are observed and unlocked. The c4 IDs below are historical, not future allocation authority. [ARC policy](https://arcm.csc.ncsu.edu/~mueller/cluster/arc/).

Setup 330278 completes in 3m21s, including an approximately 106s checkpoint download. Diagnostic 330280 completes in 58s. Repeated eight-token smoke requests produce identical full logits/tokens with finite values and ample memory margin. Seven one-token decode steps launch 8799 kernels at either context. At 128 tokens, the 106.20ms CPU annotation has 63.74% GPU interval union and 3391 adjacent kernel pairs where the next CPU launch begins after the previous kernel finishes. At 2048 tokens, the 104.45ms annotation is 95.68% GPU-busy and has 140 such pairs. These are profiler-perturbed interval observations. They justify investigating execution overhead at the short context, without supplying a latency headroom bound or unique bottleneck attribution.

The timeline separates prefill from decode. It records GEMV, pointwise/norm/rotary work, fused attention, growing-cache copies and boundary synchronization. There are no compiled regions or CUDA graph launches in A. Each decode trace includes one boundary cudaDeviceSynchronize and 21 cudaMemcpyAsync calls. The raw profiler traces and [derived summaries](../results/e014_20261108/timeline_A_128_summary.json) retain all launches, copies, memory events and gaps. An initial offline parser rejected the mirrored GPU annotation as a duplicate CPU marker. Selecting `user_annotation` explicitly corrects analysis without a GPU rerun, and a small check covers this case.

Compilation is real at the short context: one Dynamo graph, no reported graph break/recompilation and seven observed CUDA graph launches for seven decode forwards. The compiled decode trace has 3584 kernels, compared with 8799 in A/B. Every trace retains 224 fused attention kernels over prefill plus seven decode steps. The C2048 logs also show one graph, one cudagraphable partition and CUDA graph recording, but validation fails before its warmed trace is captured. Do not describe an option alone as proof of replay for that failed case.

Inductor changes fusion, scheduling and generated kernels together with graph replay. The observed kernel-count reduction is a diagnostic of bundled upstream transformations, not an isolated launch-overhead speedup. The cause of the numerical difference is not isolated. In particular, changing reduction order or intermediate fusion is plausible but has not been established as the unique cause. There is no claim that the model produced different text, that all compiled FP16 inference is inaccurate, or that Marlin is implicated.

## Timing boundaries, cold costs and the resulting limit

The predeclared primary decode timer would measure 63 cached forwards, greedy selection and common mask/buffer updates using synchronized wall clock, after token 1 is available. TTFT starts before tokenization, input H2D and cache setup/reset and ends when token 1 reaches the CPU. Request E2E additionally includes final token D2H and detokenization. Model loading, static allocation, compilation-related first request and three warmup requests are outside accepted warmed timing. Static masked capacity and cache reset/allocation differences are recorded rather than attributed solely to host overhead.

The prepared campaign has 20 raw requests per variant/context in two independent processes/orders, requiring at least 5% lower median decode latency in both series for each declared transition/context. Primary order is 128/2048 with A/B/C, then 2048/128 with C/B/A. Any qualifying transition would require the same gate on held-out text. **None of those 240 primary request samples or held-out samples is released**, because validation 330282 fails after 3m26s. There is no median, accepted speedup, primary TTFT/E2E comparison, confirmed context-length regression or held-out performance claim. Validation/reference requests that copy all logits to CPU are not substitutes for user-visible timing.

Cold records remain informative about setup scope. Successful variant processes record model/tokenizer loading around 0.57–0.69s, excluding the earlier file/parameter hash audits and Python/import startup. The first compiled request is 55.94s at 128 and 24.70s at 2048, including compilation, graph recording and inference. Those are first-request costs rather than isolated pure compilation timings. Later warmup request times are retained in raw JSON/logs but are not promoted to matched performance results. No total-process startup or compile-amortization break-even claim is made.

The final evidence-preservation job 330286 successfully archives runtime sources and compiler artifacts and passes stopped-record analysis. Its negative checker initially mishandles an intentionally missing compiler-counter key, causing that bookkeeping job to exit 1. Replacing direct lookup with an assert-based missing-key rejection fixes analysis only. The corrected local checker passes and rejects six damaged-data scenarios. The failed ARC checker/log and local attempt remain preserved. No inference is rerun for this reporting correction.

## Findings and handoff

1. The explicit dynamic-cache baseline exposes short-context gaps consistent with an execution-overhead opportunity. At the longer context the GPU is much busier in the observed timeline.
2. Static eager caching preserves the checked logits/tokens. Compiled static decoding demonstrably uses fusion and graph replay at 128 tokens, with unchanged FP16 parameters/KV.
3. The compiled longer-context path fails the declared elementwise logit test. The investigation stops before timing, so improved single-request latency remains unestablished under this contract.

The [stopped analysis](../results/e014_20261108/stopped-analysis.json), [reproduction instructions](../scripts/e014/README.md), exact commands, dependency/model/source hashes, CPU/GPU metadata, compressed raw traces, reference tensors and failed logs are preserved. Local host build/CTest and analysis checks pass. E014 adds no CUDA kernel and performs no fresh Compute Sanitizer campaign. Previous GEMM sanitizer passes are not generalized to this model/compiler. A new investigation would need a separately requested numerical characterization or another predeclared implementation choice. No tolerance relaxation, compiler-mode search, timing subset, speculative decoding or kernel tuning follows automatically.
