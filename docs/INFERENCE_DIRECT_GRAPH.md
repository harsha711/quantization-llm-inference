# E015: direct CUDA graph replay of full-model decoding

**Direct replay passes the full numerical gate and gives a small latency reduction, below the predeclared 5% target.** Keep the eager static-cache control as the default. All 160 primary request samples are retained. Neither context qualifies for held-out timing, so the prepared held-out job is cancelled without running. This is a completed performance comparison, distinct from E014's numerical stop.

The experiment implements the user-requested next mechanism after E014: capture the validated static-cache forward plus greedy argmax directly with `torch.cuda.CUDAGraph`, without `torch.compile`. Eager control E and replay candidate G inherit E014's model/request loop and both stage the current mask into a persistent input buffer. Prefill, per-step position/mask/input updates, cache reset and the host loop remain common. G warms on a side stream, captures once at the first decode position, and subsequently replays using stable token/position/mask/cache addresses. Capture warmups overwrite the same current cache entry rather than advancing generation. This uses upstream PyTorch graph replay and Transformers model/caches, with no new device kernel or local Marlin invocation. Our contribution is the bounded integration, state validation and controlled measurement.

The pinned model/tokenizer is `Qwen/Qwen2.5-1.5B` revision `8faed761d45a263340a0528343f099c05c9a4323`. The common 1,543,714,304 parameters occupy 3,087,428,608 FP16 bytes after the identical BF16-checkpoint conversion. Batch size is 1, prompt lengths 128 and 2048 and output length 64. Prefill supplies token 1 and the measured decode phase performs 63 cached forwards. The same two predeclared repeated/truncated text passages, efficient SDPA backend, explicit causal masks, FP16 KV cache and fixed EOS policy are reused. This controlled workload does not measure natural-EOS service, network latency, multiple users or model quality. The common mask staging and enforced attention path define this comparison's baseline, which is not claimed to be the fastest available serving implementation.

Final measurements use c9's RTX 5060 Ti 16 GB (sm_120), GPU UUID `GPU-02862ae3-8b7f-fb81-413c-791b5874af21`, driver 610.57.04 and AMD EPYC 9115 host. One prun rank uses 16 host threads with captured affinity. PyTorch 2.14.0+cu130, Transformers 4.57.1 and the complete E014 dependency lock match exactly. All primary points use this node/environment, with unlocked clocks and before/after clock snapshots. NVCC 13.4.92, GCC/OpenMPI versions, CPU/ISA/topology/NUMA, source/binary hashes, build flags and relevant installed runtime sources are preserved. No c7 or historical E014 median is a denominator.

Full validation checks all 9,723,904 logits at each 64-position request. E and G produce bitwise-identical logits and exact greedy tokens at both contexts on primary, held-out and repeated primary requests. Thus the unchanged elementwise bound `abs(error)<=0.03+0.01*abs(reference)` and relative-L2 bound 0.003 both pass with zero difference. Fresh eager cached endpoints also pass against uncached prefix forwards. Weights stay unchanged, cache/input pointers remain stable, occupied length advances correctly, and prompt resets do not reuse stale outputs. Candidate/reference tensors and comparison statistics are saved before numerical assertions. The retained CUDA project build/CTest and six small sanitizer checks pass on c9. These retained-kernel checks do not establish whole-model sanitizer coverage.

At each context, eight-token diagnostic traces show 7 graph launches for 7 cached forwards in G, zero in E, and no compiled regions/unique Dynamo graphs. Both variants execute 8,799 decode kernels with matching kernel-name multisets. Each trace includes the expected 224 fused attention kernels across prefill and seven decode steps. This supports replay of the same observed GPU operations. It does not isolate every library-internal choice or establish a universal bitwise guarantee.

TTFT is approximately 14.6–14.7 ms at 128 and 189.0–189.7 ms at 2048, with matched changes between -0.117% and +0.091%. Complete-request median latency falls 1.756%/1.825% at 128 and 0.888%/1.094% at 2048. Allocator peak reserved storage rises 66 MiB (+2.070%) and 86 MiB (+2.566%) respectively. These are PyTorch allocator measurements, not the total peak device footprint. Direct graph setup takes about 41.9 ms and 56.0 ms and is recorded outside warmed timing. First-request, static setup and model-load records are separate and do not constitute a compile-amortization or full-process startup result.

The result bounds this capture choice. It leaves the same device kernel count, mask construction, buffer updates and host loop. The data do not isolate whether residual preparation, GPU execution, overlap or another cost limits the benefit. No new profiling, larger capture, fusion, compiler tuning or global-optimality claim follows. E014's compiled numerical discrepancy remains unresolved and its results/tolerances are unchanged.
