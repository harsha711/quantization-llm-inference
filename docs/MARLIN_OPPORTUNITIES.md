# Marlin optimization assessment

Analysis requested 2026-11-08, based on repository checkpoint `46d7d15`, the preserved corrected E006 source, and E005-R1–E012 evidence. This review adds no kernel implementation or GPU experiment. Corrected A remains the default. Historical results and manifests remain unchanged.

**There is demonstrated room to improve throughput by changing how work reaches Marlin. There is no demonstrated general speedup from the tested Marlin kernel/launch changes, and the evidence does not prove that the kernel is optimal.** These are separate conclusions. A useful optimization need not introduce a new quantization algorithm, but it must improve a defined workload while preserving its numerical and latency requirements.

Quantization defines a compressed representation and its reconstruction error. The mathematical representation can be implemented on different processors. Its efficient execution depends on supported instructions, conversion throughput, register/shared-memory capacity, caches and memory bandwidth. In this project, W4A16 means packed INT4 storage followed by FP16 reconstruction and FP32 accumulation. It does not mean that the matrix multiplication uses native four-bit arithmetic. Replacing this with FP4 weights or quantized activations would change the numerical problem and require model-quality evaluation, beyond the current FP64 implementation check.

The exact G128 storage model is `0.5 + 2/128 = 0.515625` bytes per weight, including FP16 scales. FP16 storage divided by this value is `3.878787...`. This is a storage ratio, not a speedup ceiling against an arbitrary FP16 implementation. Each tested rectangle stores 23,248,896 bytes, or 22.171875 MiB, of weights/scales. Avoiding their transfer, reusing them for more rows, and decoding them efficiently are distinct opportunities.

FreeToken is relevant to the orchestration question. Its authors describe expert caching, overlapped prefill transfers, and a measured-bandwidth policy that divides missing MoE experts between GPU transfer/execution and CPU execution. This supports using host memory and multiple processing resources when the model exceeds VRAM. It does not establish that all parameters reside in the GPU or that a dense GEMM kernel becomes faster. Its policy explicitly depends on the hardware. The cited sources establish the system mechanisms and RTX 30-series support, but this review does not verify the particular 12 GB demonstration mentioned in the request. [FreeToken paper](https://arxiv.org/html/2608.16157v1), [project](https://github.com/FlashML-org/FreeToken).

The saved evidence separates several possible improvements:

| Opportunity | Evidence and interpretation | Assessment |
|---|---|---|
| More concurrent blocks | E005-R1 increases observed concurrency but misses the fixed 5% square-case latency gate. Extra partition/reduction work accompanies the larger grid. | Do not retry unchanged occupancy tuning. Low occupancy alone is insufficient evidence. |
| Restricted launch choice for reused weights | E005-R2 confirms roughly 13.3% lower latency in the stronger repeated-matrix case. E008 retains roughly 13.4% for one matrix, but only 1.3–2.4% with four. The reverse four-matrix case regresses. | A real, restricted opportunity. It does not justify general decoding dispatch. |
| Remove unused terminal fragment loads | E007 reduces participating shared loads, but issued work increases and latency gains fail to reproduce. | Keep the negative result. Fewer source operations do not necessarily mean a faster binary. |
| Improve large-M execution | E011 observes nearly unchanged DRAM reads, increased instruction/Tensor work, and 255 registers per thread at M128. E012 cannot establish critical-path phase ownership. | Plausible scope for a controlled experiment, without a justified rewrite yet. |
| Batch ready activation rows | E010 processes four times the rows at M16 for only 3.4–5.0% more complete-cycle time than M4. | Strongest existing evidence for orchestration, subject to queueing and dependencies. |

All latency comparisons above retain their own matched controls. The E009 3.60–4.40× cyclic advantage over pre-materialized FP16 cuBLAS is predominantly upstream Marlin performance. It is not an improvement contributed by our launch experiments. E011's small-M DRAM throughput of approximately 85–88% of the profiler's sustained-peak metric makes a large gain from merely increasing block count less compelling. This percentage is neither a rigorous latency headroom bound nor a full-machine roofline. Tensor-active percentages at M128 likewise do not measure useful peak FLOP utilization.

The batching calculation uses the unchanged corrected A in E010, four distinct matrices, G128, both rectangles, two reversed series, ten warmup cycles and 100 samples per row. Define `T4` and `T16` as the median complete-cycle times at M4 and M16. The useful-row throughput ratio is `(16/T16)/(4/T4) = 4*T4/T16`. Recomputed from raw samples, it is 3.8128/3.8105 for K4096/N11008 and 3.8663/3.8678 for K11008/N4096, in series order. The arithmetic is saved in [batch-calculation.json](../results/reporting/marlin_opportunities/batch-calculation.json).

This calculation is not a measured scheduler speedup. E010 does not measure request arrivals, batch formation, activation gathering, attention, KV-cache traffic or tokens per second. It does show that considerably more useful work fits into nearly the same GEMM time. Requests already ready at the same layer can potentially share that work. Consecutive autoregressive tokens from one request generally cannot be batched because the next token depends on the preceding result. Waiting to fill a batch can increase latency. Speculative decoding would introduce separate draft/acceptance costs and is not evaluated here.

Source inspection explains why generic optimization lists are insufficient. The archived patched `marlin_template.h` already pipelines asynchronous global copies, shared/register loads, dequantization and matrix instructions. Its phase-transition barrier is the E006 correction and must remain. Offline weight layout conversion is already part of the integration. CUDA graph timing already reduces host launch gaps. [Upstream Marlin](https://github.com/IST-DASLab/marlin) documents the same general overlap/layout strategy, although its original reduction choices are not a substitute for this repository's FP32 reduction contract.

There is one concrete kernel-level question that remains open without requiring a partition rewrite. The archived `marlin.cu` selects the first valid entry from ordered tile configurations. Its large-M priorities are `(Ktile,Ntile,threads) = (64,256,256), (64,128,128), (128,64,128)`. The bounded local build includes those alternatives, but the current wrapper requests automatic selection and E010/E011 did not compare them. First-valid selection is not a proof of latency optimality on this GPU. A separately scoped comparison of the current M128 tile with one preselected existing alternative could test whether a smaller tile's resource footprint outweighs its extra work. Measure the actual resources, preserve the corrected body/rounding/reduction, validate the forced entrypoint and guards, then compare complete four-matrix cycles with fresh matched controls, reversed orders and held-out operands. Require at least 5% lower median in both series and report regressions. This is an untested hypothesis, not a promised gain or an authorized implementation in this review.

For orchestration, the most supported next question is whether four independent, already-ready M4 requests sharing each weight matrix complete faster as one M16 call. A fair test would compare identical concatenated activation rows and all outputs, keep the same four-matrix workload, include required gather/scatter work, and separately account for queueing. It would directly test the opportunity suggested by E010. Concurrent streams alone cannot guarantee a gain when operations compete for the same bandwidth. Combining adjacent projections or fusing an epilogue is another possible direction only after a real layer trace establishes removable launches or intermediate traffic. This repository has no such end-to-end trace.

For a definite answer, define the scope as the numerical contract, GPU, workload and allowed change. A repeatable win answers that bounded question positively. Exhausting a small predefined candidate set can reject that set. Neither a few failed candidates nor high utilization proves that all implementations are optimal. The present answer is therefore: scheduling/reuse opportunities are supported, the known launch improvement is restricted to short reuse distance, and further kernel headroom remains unresolved.

Verification: E005-R1, E005-R2 timing/profile, E007 and E008–E012 analyzers pass on temporary copies. E005-R2 and E008–E012 corruption checks also pass. E012 retains all eight failed sampling-quality decisions. [Review logs](../results/reporting/marlin_opportunities/) record these offline checks. Host-only build and CTest pass. No GPU allocation, current ARC scheduler check, CUDA build, new sanitizer run, model inference, native-FP4 comparison or profiling retry was performed. The absence of these checks limits new performance claims, not the validity of the saved bounded results.
